# Accessibility Statement — Code Journey

**Scope:** WCAG 2.1 AA is a product requirement (PLAT-05). This page states what is
verified, how, and what is still open. Last updated: 2026-09-03 (Phase 7).

## What is automated

`tests/e2e/accessibility.spec.ts` runs on every E2E pass (Chromium, `@axe-core/playwright`):

- **axe-core WCAG 2.1 A + AA scans** on the core pages: home, learn index, a lesson,
  a challenge workspace, login, register. Critical and serious violations fail the suite.
- **Keyboard navigation test**: the skip link is the first tab stop; a keyboard-only
  path reaches the challenge Run button and activates it with Enter, producing a
  visible live-region status change.
- The same E2E suite covers the full student journey with keyboard-only run
  activation (`critical-path.spec.ts`, "keyboard-only run reaches the verdict panel").

## What was manually checked

- **Focus visibility**: interactive elements use visible focus states (browser default
  outlines are not suppressed anywhere in the CSS; Tailwind `focus:`/`focus-visible:`
  utilities are used on custom controls).
- **Live regions**: the challenge verdict panel announces results through an
  `aria-live` status region; the mobile action bar (07-07) is a `role="status"`
  region announcing run progress and the verdict summary without switching tabs;
  mobile tab switches and mentor hints use role/status or alert patterns.
- **Mobile editor rendering (fixed 07-06):** the challenge workspace renders exactly
  one branch per viewport (client-observed via `useSyncExternalStore`), so the mobile
  tab layout mounts a visible, non-zero editor — verified by E2E at 375/390/430/768/
  1024/1280/1440 px (`tests/e2e/mobile-editor.spec.ts`), including type → run → verdict
  on a phone-sized viewport. The header announces session-hydration state via
  `aria-busy` (07-08).
- **Semantics**: lesson content renders through MDX with heading landmarks, nav
  breadcrumbs with `aria-label`, and `<article>`/`<main>` landmarks.

## Known gaps

- **No screen-reader deep pass yet.** axe-core catches many issues but not reading-order
  quality, verbosity, or VoiceOver/NVDA ergonomics. A guided pass with real assistive-
  technology users is planned before calling AA "conformance" (vs. "audited to AA").
- **Scans cover core pages only.** Dashboard, discussion threads, and error pages are
  not yet in the automated scan set.
- **Contrast tuning is token-level.** We raised muted text from zinc-500/600 to
  zinc-400 (≥4.5:1 on the zinc-950 background). Rich content inside user-generated
  MDX is not contrast-policed at runtime.

## Running the audits

```bash
pnpm exec playwright test tests/e2e/accessibility.spec.ts   # axe + keyboard
pnpm exec playwright test tests/e2e/                        # everything incl. a11y
```

The a11y spec needs only a reachable app server (Playwright starts one); the
challenge-page scan does not require Docker.
