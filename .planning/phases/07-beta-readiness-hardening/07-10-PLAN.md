# Plan 07-10: Production Code Execution Architecture

## Decision (RESOLVED 2026-09-03)

**Production execution: SELF-HOSTED JUDGE0.**
- **Local:** continue with the existing hardened Docker runner (development, automated tests, local debugging). Do not replace it prematurely.
- **Private beta:** continue hardened Docker, but only on a **dedicated sandbox worker host** that does **not** share the Docker socket/host with the web application. Treat the Docker socket as host-level privilege.
- **Public production:** migrate to **dedicated Judge0 execution infrastructure** on its own host — separate from the web app, the primary DB, and sensitive secrets.
- **No production infra introduced in Phase 7.** Phase 7 implements the beta-safe boundary (local runner intact, dedicated sandbox host for beta) and **documents** the production migration, deployment/config requirements, and a verification checklist. Actual Judge0 deployment is deferred to a later phase.

## Objective

Define a public-production-safe execution architecture and make the current dev sandbox
explicitly scoped to local/beta. The web tier must never receive privileged execution access;
production moves untrusted code to appropriately isolated infrastructure.

## Threat → behavior

- **Threat:** the current worker spawns `docker ... run` and therefore needs the Docker
  socket. Docker socket access is effectively host-root: a sandbox escape or a compromise of
  the worker grants host control. Acceptable on an isolated dev machine, **not** on a host
  that also serves user data.
- **Existing behavior (verified):** `src/workers/sandbox.ts` runs `spawn("docker", ["run",
  "--network","none", ...])`. Hardening is strong (no network, read-only root, tmpfs,
  `--cap-drop ALL`, `no-new-privileges`, non-root, PID/mem/cpu limits, host-side timeout,
  output cap, `--rm`). But it depends on the host's Docker daemon.
- **New behavior:** the sandbox worker is **isolated on its own host** with only the Docker
  socket and no access to user data or app secrets. For public production, untrusted code
  executes behind a stronger isolation primitive. The web tier continues to enqueue jobs and
  read verdicts only.

## Candidate comparison (evidence-based; 2026 research)

| Candidate | Isolation | Ops complexity | Cost | Startup latency | Language support | Fit |
|---|---|---|---|---|---|---|
| Current hardened Docker (as-is) | Weakest (shared kernel, no seccomp hardening beyond default) | Low | Low | ~0.5–2s cold | Broad (image-defined) | **LOCAL/beta only** |
| Dedicated sandbox host + hardened Docker | Same as Docker, but physically isolated | Medium | Medium | same | Broad | **BETA** |
| gVisor (user-space kernel) | Strong (syscall interception) | Medium–high | Medium | ~100–500ms | Broad | Public (single-host per feature) |
| **Firecracker microVM** | **Strongest (own kernel, hardware isolation)** | High | Medium | ~150ms–1s | Broad via images | **PUBLIC (recommended)** |
| **Judge0** (self-hosted, can back with Firecracker/gVisor) | Strong when backed by a sandbox | Medium | Medium (open-source, self-host) | ~0.5–2s | **Polyglot, purpose-built for judging** | **PUBLIC (recommended)** |
| Hosted microVM (E2B / Vercel Sandbox) | Strong | Low | **Paid, per-run** | low | Broad | Fast-path but vendor cost/lock-in |

**Decision (confirmed above):** hardened Docker for local + private-beta (on a dedicated
sandbox host), and **self-hosted Judge0** for public production — matching the roadmap
(docs/STACK.md: "Judge0 is the reference") and avoiding vendor lock-in. Judge0 does **not**
by itself solve security; the requirements below are mandatory for the production design.

## Environment split

- **LOCAL:** hardened Docker runner (unchanged): development, automated tests, local debugging. Env-gate the worker: `SANDBOX_DOCKER_HOST` (e.g. `tcp://sandbox-host:2375`) and a host-scoped `SANDBOX_IMAGE`; default stays local.
- **PRIVATE BETA:** hardened Docker worker on a **dedicated sandbox worker host** with the Docker socket and **no user-data credentials**. The web app must not share the Docker socket/host with the worker. Architecture: Internet → Web App → Postgres Queue → Dedicated Sandbox Worker Host → Hardened Container. Never run untrusted code on the web host.
- **PUBLIC PRODUCTION:** migrate to a **dedicated Judge0 host** behind the execution queue/API, isolated from the web app, the primary DB, and secrets. Swap the executor behind `src/workers/execute.ts` (the single execution seam) for a Judge0 adapter; the typed `JobPayload`/verdict interface is unchanged. Actual deployment is deferred beyond Phase 7.

## Judge0 security requirements (production design checklist)

Judge0 does NOT automatically make execution secure. The production architecture must address all of:

- **Host isolation** — Judge0 on its own host/microVM, separate from the web app, primary DB, and secrets.
- **Network isolation** — no (or strictly allow-listed) egress for executed code; Judge0 API reachable only from the queue/worker.
- **CPU limits** — runtime CPU cgroup/`setrlimit` per submission.
- **Memory limits** — per-submission memory ceiling + OOM kill.
- **Process limits** — PID/file-descriptor caps to stop fork bombs and fd exhaustion.
- **Execution timeouts** — wall-clock and CPU time out; kill + timeout verdict.
- **Output limits** — stdout/stderr truncation to prevent memory/verdict flooding.
- **Filesystem isolation** — ephemeral, read-only rootbase + tmpfs scratch; no host FS reachable.
- **Container/microVM isolation** — choose the sandbox backend deliberately (Firecracker/gVisor) and justify it.
- **Privilege dropping** — non-root, dropped caps, `no-new-privileges`, no privileged containers.
- **Secret isolation** — executed code never sees env/secrets; the Judge0 host has no application credentials.
- **No access to app internals** — no Postgres, no internal services, no control plane, from executed code.
- **Job cleanup** — containers/microVMs always torn down (`--rm`/GC), no persistent artifacts.
- **Queue abuse** — per-user/IP rate limits + concurrency caps (pairs with 07-03).
- **Execution concurrency** — bounded concurrency; a burst cannot flatten the host.
- **Monitoring** — structured logs of job lifecycle; alerting on failures/abuse.
- **Failure handling** — worker crash, daemon loss, image failure all map to a clear verdict, never a silent hang.
- **Stale jobs** — reclaim/requeue or fail jobs whose worker died (stale threshold + attempts cap).
- **Result integrity** — verdicts cannot be forged by submitted code (fixed by 07-01) and are written server-side.

**Conclusion:** the production architecture must prevent student code from gaining access to application infrastructure, not merely isolate it from the host kernel.

## Files likely affected

- `src/workers/execute.ts` — unchanged interface; a future Judge0 adapter implements the same

- `.env.example` — add placeholder `SANDBOX_DOCKER_HOST` / `SANDBOX_IMAGE`.

## Tests / verification

- Unit: `runSandboxed` builds the docker args correctly when a `SANDBOX_DOCKER_HOST` is set
  (no secrets in the command) and preserves the hardening set.
- Integration: the malicious-sample suite still passes against the default host.
- Evidence: a security note that production requires the isolated host + Judge0/microVM; do
  not claim production-grade for Docker-socket.

## Rollback

Reverting keeps the local Docker worker. The executor seam (`execute.ts`) means a half-built
Judge0 adapter does not affect locals. Additive env vars; no data change.

## Security implications

Primarily a **scoping** fix: makes explicit that untrusted code runs on an isolated host,
never on the web/server tier. The `-H` docker host must be a trusted, dedicated endpoint; the
worker must be the only client. Never expose the Docker socket publicly; never run the worker
with user-data DB credentials.
