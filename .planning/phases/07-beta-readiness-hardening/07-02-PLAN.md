# Plan 07-02: Submission Authorization (IDOR) + Require-Auth-to-Run

## Decision (RESOLVED 2026-09-03)

**Auth required to run: YES.** Code execution requires an authenticated account. Anonymous
users retain read access to public curriculum and challenge instructions but **cannot submit
code for execution**. Public curriculum reading stays anonymous.

## Objective

Close the submission read IDOR and prevent anonymous-run resource abuse. After this plan,
only an authenticated owner (or admin when explicitly justified) can read a submission,
and challenge submissions require a session. Authentication is enforced **server-side**
(never client-side route guards alone); submission ownership is preserved and verified when
retrieving results; role/identity is never trusted from the JWT when a fresh DB check is
needed.

## Threat → behavior

- **Threat:** `GET /api/challenges/run/[submissionId]` has no auth/ownership check. Any
  caller who learns a submission id can read its verdict + output. UUIDs make guessing
  impractical, but the authorization is semantically wrong.
- **Existing behavior:** the GET returns `404` if missing, `202` while pending, else the
  verdict + `output` — with no session check. The POST allows anonymous runs
  (`session?.user?.id ?? null`) and stores `userId: null`.
- **New behavior (DECIDED):**
  - Challenge runs require an authenticated session. `POST /api/challenges/run` → `401`
    when anonymous. Anonymous visitors can still read public lessons/challenges; only the
    code-run step needs an account.
  - `GET /api/challenges/run/[submissionId]` → `401` when anonymous; `404` when the
    submission isn't the caller's own (hide existence); `200/202` for the owner. Admin
    access only if a requirement explicitly demands it (currently none — do NOT add one).
- **Rationale:** requiring auth to run simultaneously fixes the IDOR, closes anonymous
  container-spawn abuse (pairs with 07-03 rate limiting), and makes attribution
  unconditional.

## Current implementation

- `src/app/api/challenges/run/route.ts` — POST builds a `JobPayload`, inserts a submission
  with `userId: session?.user?.id ?? null`, enqueues.
- `src/app/api/challenges/run/[submissionId]/route.ts` — GET reads by id, no session.
- `src/lib/execution/queue.ts` — `getLatestJobForSubmission`, `completeJob` mirror verdict;
  `completeJob` only records progress when `submission.userId` is set.
- `src/components/challenge/ChallengeWorkspace.tsx` — `run()` POSTs; on `401` should show a
  login prompt rather than a generic error.

## Files likely affected

- `src/app/api/challenges/run/route.ts` — require `auth()`, return 401 if absent; keep
  inserting `userId = session.user.id` (now always set).
- `src/app/api/challenges/run/[submissionId]/route.ts` — require session; load submission;
  if `submission.userId !== session.user.id` return 404; else return verdict.
- `src/lib/execution/queue.ts` — `completeJob` progress hook can assume `userId` present
  (nullable check can stay as defense-in-depth).
- `src/components/challenge/ChallengeWorkspace.tsx` — handle `401` (show "log in to run").
- `tests/integration/submissions-authz.test.ts` (new).

## Implementation steps

1. POST: call `auth()`; if no user → `401 { error: "log in to run" }`. Use
   `session.user.id` for `userId`.
2. GET: `auth()`; if no user → `401`. Load submission; if
   `submission.userId !== session.user.id` → `404` (do not reveal ownership). Add a
   defensive index/lookup by `id` (already covered by PK).
3. Keep the job-id endpoint (`getLatestJobForSubmission`) but only allow reading when the
   caller owns the submission.
4. Update the anonymous E2E tests that currently rely on anonymous runs
   (`tests/e2e/anonymous.spec.ts`, `critical-path.spec.ts`) to sign in before running.
5. Update `ChallengeWorkspace` to surface a login CTA on `401`.

## Tests (integration) — regression set

- **Anonymous → cannot run:** anonymous POST `/api/challenges/run` → `401`, and **does not enqueue** an execution job (assert no `execution_jobs` row created).
- **Authenticated A → can run:** A POST → `202` with `submissionId`.
- **Authenticated A → can read own submission:** A GET `/api/challenges/run/[A's submissionId]` → `200/202`.
- **Authenticated B → cannot read A's submission:** B GET A's `submissionId` → `404` (existence hidden).
- **Anonymous GET any submissionId** → `401`.
- **Unauthorized request → no enqueue:** a POST without a session (or with a forged/invalid session) results in `401` and no `execution_jobs` row.
- **Ownership preserved:** submission `userId` equals the authenticated caller's id, and results retrieval only returns rows owned by the caller.

## Rollback

Reverts to anonymous-run + no-ownership. No schema change. Gate anonymous-run promotion
behind a config flag if beta wants a read-only anonymous trial later — but default to
auth-required.

## Security implications

Removes the IDOR and makes the run path abusable only by authenticated users (then
rate-limited via 07-03). Aligns with "never trust client-side authorization." No secrets
introduced.
