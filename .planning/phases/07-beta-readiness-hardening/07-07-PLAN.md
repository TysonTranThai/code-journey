# Plan 07-07: Improved Mobile Challenge Run Flow

## Objective

Fix the clunky mobile loop where "Run code" only lives in the Instructions tab, forcing
Instructions → Code → Instructions → Run → Output. Provide a persistent, discoverable,
thumb-friendly run action reachable from Code and Output without leaving the editor.

## Current UX (verified)

- In `src/components/challenge/ChallengeWorkspace.tsx`, the mobile branch renders
  `MobileTabs` with three tabs: Instructions (content = instructions + `runButton`), Code
  (editor only), Output (verdict + error). The `runButton` element is duplicated inside the
  Instructions tab content only. A learner on the Code tab has no Run control visible.

## Design decision

- Add a **persistent mobile action bar** pinned (sticky) at the bottom of the workspace on
  the tabbed (mobile/tablet) layout, always visible across Instructions/Code/Output. It holds
  a single, always-enabled **Run code** button (with a `Running…` state) and, when a verdict
  exists, a "view results" action. This keeps Run reachable without switching tabs, is easy
  to thumb-reach, and is a single obvious affordance.
- Rationale vs alternatives: a run inside Code still requires leaving the output/instructions
  context; a FAB is less discoverable and awkward for a primary action; a sticky bottom bar is
  standard for a primary action on mobile, keyboard-accessible (real button in tab order),
  and stateful (mirrors running/error).

## Current implementation

- `runButton` is declared once and only placed in the Instructions tab content.

## Files likely affected

- `src/components/challenge/ChallengeWorkspace.tsx` — add a sticky mobile action bar (Run +
  status), keep the desktop layout unchanged.
- `src/components/challenge/MobileTabs.tsx` — expose the active tab so the bar can react to
  it, or render the bar outside the tablist (recommended: place the bar as a sibling under
  the mobile tablist so it is always visible).
- `tests/e2e/mobile-run-flow.spec.ts` (new).

## Implementation steps

1. Extract the `runButton` so it can render inside the mobile action bar (and optionally the
   Code tab) without duplication, reusing the existing `run` handler and `runState`.
2. Add a sticky bottom bar (e.g. `sticky bottom-0`) inside the `lg:hidden` branch showing:
   the Run button, the current phase (`Running…` / id) and an error/verdict status hint.
3. If a verdict exists, the bar can include a "View output" button that switches the active
   tab to Output (note: tab state lives in `MobileTabs`; lift it via a controlled `active`/
   `onChange` prop so parent code can switch tabs).
4. Keep the desktop `lg:grid` layout and its inline Run button unchanged.
5. Ensure the bar is keyboard-navigable and announces state via an `aria-live` region.

## Tests (Playwright, mobile widths)

- With the Code tab active, the Run button is **visible** (not just in Instructions).
- Pressing Run while on Code starts a run and shows `Running…`.
- The verdict appears in Output and the bar's "View output" switches the active tab to Output.
- Loading + error states render, and the bar remains visible/sticky while scrolling.
- Keyboard: Tab reaches the bar's Run button; Enter activates it.
