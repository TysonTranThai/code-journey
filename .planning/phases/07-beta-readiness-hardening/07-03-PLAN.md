# Plan 07-03: Atomic Database-Backed Rate Limiting

## Objective

Add real rate limiting to the abuse-prone endpoints (register, login, password reset,
challenge run) and make the existing mentor quota check+record atomic. Beta-appropriate,
upgradeable to a distributed limiter later without changing call sites.

## Threat → behavior

- **Threat (register/login/password reset):** unlimited unauthenticated POSTs → account
  spam, bcrypt cost-12 CPU DoS, and reset-token DB flooding.
- **Threat (challenge run):** each POST spawns an isolated execution workload; unlimited
  anonymous (now, post-07-02, authenticated) runs → resource/DB exhaustion.
- **Existing behavior:** only `src/lib/mentor/rate-limit.ts` limits anything (per-user
  daily for the mentor), and its `checkMentorQuota` → `recordMentorRequest` is a separate
  read then insert — a non-atomic TOCTOU window allowing quota overrun under concurrency.
- **New behavior:** a DB-backed fixed-window counter with an **atomic
  `INSERT … ON CONFLICT DO UPDATE SET count = count + 1`** upsert used as the single
  check-and-increment primitive. Endpoints enforce per-IP (auth-agnostic) and, where a user
  is known, per-user limits. Returns `429` with a `Retry-After` header on exhaustion.

## Design decisions

- **Storage:** a `rate_limit_events` table (or a `limited_keys` counter table) with a
  primary key `(scope, key, window_start)` and a `count`. A single upsert in a transaction
  both atomically increments and tells us the resulting count, eliminating the check-then-
  act race. Chosen over Redis for beta: no new infra, no vendor lock-in; the counter store
  is behind an interface so Redis can be swapped in for distributed deployment.
- **Keys:** `scope:ip:<addr>` for register/login/reset; `scope:user:<id>:ip:<addr>` for
  challenge runs. Keyed by IP where the caller may be unauthenticated, and by user+IP for
  runs to be fair yet still throttle a single actor.
- **Limits (defaults, tuned later):** register 5/hour/IP; login 10/hour/IP (plus a
  short-burst 5/min); reset 5/hour/IP; challenge run 20/day/user + 5/min/user+IP. All
  configurable constants.
- **Window:** fixed window (hourly/daily) keyed by `window_start = epoch_floor(timestamp /
  bucket_ms)`. Burst limits use a separate small window (per minute).
- **HTTP:** on exhaustion, `429 { error: "Too many requests. Try again in Ns." }` with
  `Retry-After` header — so the UI can show a friendly countdown.

## Current implementation

- `src/lib/mentor/rate-limit.ts` — `checkMentorQuota` (SELECT count) then
  `recordMentorRequest` (INSERT). Non-atomic.
- No limiter elsewhere.

## Files likely affected

- `src/lib/db/schema.ts` (+ `rate_limit_events` table + types), a migration.
- `src/lib/rate-limit/limiter.ts` — `consume(scope, key, limit, windowMs)` returning
  `{ allowed, remaining, resetMs }`; uses a transaction with `INSERT … ON CONFLICT`.
- `src/lib/mentor/rate-limit.ts` — refactor to use `consume` (atomic; keep per-user daily
  limits for hint/explain).
- `src/server/actions/auth.ts` — wrap register/login/reset actions with limiter calls.
- `src/app/api/challenges/run/route.ts` — consume before enqueue.
- `tests/integration/rate-limit.test.ts`.

## Implementation steps

1. Add `rate_limit_events` table + index; generate a migration.
2. Implement `consume(...)` with the atomic upsert; add a `resetAfterMs`/`Retry-After`
   helper.
3. Wire register, login (with a burst limiter), password reset.
4. Wire challenge run (per user+IP); keep mentor per-user daily but via `consume`.
5. Return `429` + `Retry-After` from server actions and the run route; surface a friendly
   message in the UI.
6. Unit/integration tests for boundary conditions (exactly at limit, over, reset, atomicity
   under concurrent calls).

## Tests

- Register/login/reset: hit the limit → 429; below → allowed; window rolls over → allowed.
- Challenge run: limit per user+IP enforced; concurrent requests never exceed the window.
- Mentor: refactored to `consume`; existing mentor quota tests still pass; add a
  concurrency assertion that count never exceeds the limit.
- Assert `Retry-After` header present on `429`.

## Rollback

Schema addition is additive (new table); reverting limiter wiring is independent. The new
table can be dropped without touching existing data.

## Security implications

Prevents unauthenticated CPU/resource DoS on auth + run endpoints; makes mentor limits
correct under concurrency. No secrets. Store is isolated behind an interface for a future
Redis/upstash swap (distributed) without call-site changes.
