# Plan 07-08: Static Public Curriculum Delivery

## Objective

Allow public routes (/, /learn, /learn/[track], /learn/[course], /learn/[lesson]) to be
statically generated / cached, while keeping authenticated surfaces (user menu, dashboard,
challenge state) working. This restores SEO-friendly static HTML and removes the per-request
server render of public content.

## Threat → behavior

- **Threat (perf/SEO):** the root layout's `SiteHeader` calls `await auth()`, which forces
  the *entire* route tree to render dynamically (measured: every route is `ƒ` in the build).
  Public lesson HTML is re-rendered per request (no SSG/ISR cache), contrary to the stated
  goal of caching public lessons.
- **Existing behavior (verified):**
  - `src/app/layout.tsx` renders `<SiteHeader />` in the shared root layout.
  - `src/components/layout/SiteHeader.tsx` is an async server component calling `auth()`,
    then passing `signedIn`/`userName` to the client `SiteHeaderClient`.
  - Build output: all 19 routes are `ƒ` (dynamic) except `robots.txt`/`sitemap.xml`.
- **New behavior:** the session read is removed from the server layout. The header becomes a
  client component reading auth state via NextAuth's `SessionProvider`/`useSession()`, with a
  static-safe loading fallback. Public pages no longer touch `auth()` in their server tree, so
  they can be statically generated (SSG) and cached. Pages that genuinely need server auth
  (dashboard, challenge `signedIn`, discussions) still call `requireUser`/`auth()` themselves.

## Design decisions

- **Server/client boundary:** keep the server layout static (no `await auth()`). Render a
  client `SiteHeader` wrapped in `<SessionProvider>` so auth state hydrates client-side. The
  header briefly shows a neutral/loading state then reflects `signedIn` — acceptable and
  standard, and it never gates public content.
- **No duplication:** the existing `SiteHeader` server shell is replaced by a client
  component (or the server component is dropped and the client headers are mounted directly).
  The per-route `auth()` calls that drive *real* authorization (guards) remain exactly where
  they are.
- **Caching:** add `export const revalidate` or rely on static generation for public pages;
  do not force `dynamic`. For lessons, `generateStaticParams` (or ISR via `revalidate`) to
  pre-render the content-driven routes without a DB hit.

## Current implementation

- `src/app/layout.tsx` — static layout except it mounts `<SiteHeader />` (which reads auth).
- `src/components/layout/SiteHeader.tsx` — async, calls `auth()`.
- `src/components/layout/SiteHeaderClient.tsx` — client, receives `signedIn`/`userName`.

## Files likely affected

- `src/app/layout.tsx` — wrap children in `<SessionProvider>`; render the client header.
- `src/components/layout/SiteHeader.tsx` — convert to a client wrapper using `useSession()`
  (drop the server `auth()` call), or delete and mount client directly.
- `src/app/providers.tsx` (new) — a client `SessionProvider` wrapper if not already present.
- Public route pages — add `generateStaticParams` / `revalidate` where applicable.
- `tests/e2e/static-public.spec.ts` (new).

## Implementation steps

1. Add `SessionProvider` (from `next-auth/react`) in a client `Providers` component and wrap
   the root layout.
2. Convert `SiteHeader` to use `useSession()` (`status`/`data`) instead of the server
   `auth()`; render a stable, non-flickering header with an `aria-busy`/static fallback while
   loading. Remove the server `await auth()`.
3. Verify each public route no longer includes `auth()` in its server tree. The challenge
   page currently calls `auth()` for `signedIn` — split that so the page itself is static and
   `signedIn` is derived client-side, OR keep the challenge dynamic but verify the **public
   pages** (`/`, `/learn`, track, course, lesson) become static.
4. Add `generateStaticParams`/`revalidate` to the content-driven public routes (track, course,
   module, lesson) so they pre-render without DB.
5. Rebuild and confirm the public routes flip to `○` (Static) while dashboard/challenge stay
   `ƒ` (Dynamic).

## Rollback

Revert to the server `auth()` header. No schema/data change. The `SessionProvider` is
additive and harmless.

## Security implications

Removing a server session read in favor of a client-hydrated header does **not** weaken
authorization: every protected action/page still enforces server-side via `requireUser`/
`requireRole`/`auth()`. Public content remains indexable; private pages remain `noindex`
(unchanged). The header's signed-in state is cosmetic and never a trust boundary.
