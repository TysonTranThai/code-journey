# Plan 07-04: Password Reset Email Adapter

## Objective

Make password reset work for real users without server-console access, while keeping token
security intact and **not choosing a provider** prematurely. Introduce an email abstraction
whose default is a safe dev console transport; the production transport is selected by env
at beta.

## Threat → behavior

- **Threat:** password reset is currently unusable for a real user — the link is logged to
  the server console. Shipping that to beta would tell users "check your email" and deliver
  nothing.
- **Existing behavior:** `requestPasswordReset` (in `src/server/actions/auth.ts`) inserts a
  hashed token and `console.log`s the link. Token mechanics (`src/lib/auth/reset-token.ts`)
  are already correct: 32 random bytes, only sha256 stored, 1h expiry, single-use
  (`usedAt`), enumeration-safe (identical response regardless of account existence).
- **New behavior:** `requestPasswordReset` sends through an `EmailSender` adapter. In dev,
  the default adapter writes the link to the transport log (as today). Once a provider is
  configured via env (`EMAIL_*`), the adapter sends a real email. No provider is hard-wired;
  only the interface and a console sender land in Phase 7.

## Design decisions

- **Adapter interface:** `EmailSender.send(to, { subject, text, html })` returning
  `Promise<void>`. A `consoleEmailSender` is the default (dev + tests) — deterministic, no
  network, no credentials.
- **Provider selection by env (later):** when `EMAIL_PROVIDER` and its credentials are set,
  a concrete sender is built and returned by `getEmailSender()`. Phase 7 ships only the
  console sender and the seam; a real provider (SMTP/Nodemailer or a transactional API)
  is a single adapter to add — env-based, secrets server-side.
- **No fabricated credentials:** anything provider-related stays placeholders in
  `.env.example`.

## Current implementation

- `src/server/actions/auth.ts` — `requestPasswordReset` logs the link via `console.log`.
- `src/lib/auth/reset-token.ts` — token generation/hashing/expiry/single-use (correct).

## Files likely affected

- `src/lib/email/transporter.ts` — `EmailSender` interface + `consoleEmailSender` +
  `getEmailSender()` (env-gated stub for a future provider).
- `src/lib/email/send-password-reset.ts` — builds the link from `siteConfig.url` +
  `reset/<token>` and calls the sender.
- `src/server/actions/auth.ts` — replace `console.log` with `sendPasswordReset(email, token)`.
- `src/lib/site-config.ts` — ensure a public base URL is available for the link.
- `tests/unit/email-transport.test.ts`.

## Implementation steps

1. Define `EmailSender` and `getEmailSender()`; default console sender (logs the composed
   email, never the raw reset token if avoidable — actually dev may log it to aid local
   testing; gate by non-production).
2. Add `sendPasswordReset(email, rawToken)` that builds the absolute link and sends.
3. Swap the `console.log` in `requestPasswordReset` for `sendPasswordReset`.
4. Keep the enumeration-safe return message unchanged.
5. Add `EMAIL_*` placeholders to `.env.example` and a comment that a real sender is a
   single-adapter change.

## Tests

- Unit: the console sender records the composed email (recipient, link present). Use a
  mocked `getEmailSender` for the action so the test never needs a real mailbox.
- Unit: `requestPasswordReset` calls the sender exactly once with the right address, and
  still returns the same response for existing and non-existing accounts (enumeration-safe).
- Unit: token is single-use and expiring (already covered; re-assert after refactor).

## Rollback

Additive; revert swaps the action back to `console.log`. No schema change; token mechanics
unchanged.

## Security implications

Token remains hashed/expiring/single-use and never returned to the client. Secret-bearing
provider credentials only exist behind `EMAIL_*` env (server-side). Default transport is
dev-only and must be gated so it is never active in production without an explicit provider
(assert at startup in prod mode).
